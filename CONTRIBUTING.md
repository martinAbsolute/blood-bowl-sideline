# Contributing to Blood Bowl Sideline

**Opening an issue is a great way to contribute**: report a bug, suggest a feature, point out a rules discrepancy, or help improve English and Ukrainian translations. Pull requests and forks are welcome too.

This community project is maintained as time allows. There is no commitment to respond to issues, review or merge pull requests, provide support, or deliver a feature on a particular schedule. Keep contributions focused and describe the problem they solve.

## Development environment

You need Git, Node.js **24**, the pnpm version pinned in `package.json`, and a Convex account with your own development deployment. Windows, macOS, and Linux are supported; no production credentials are needed.

1. Fork the repository when it becomes public, or clone it using your existing access. Create a branch such as `codex/improve-roster-search`.
2. Enable Corepack and install the locked dependencies:

   ```sh
   corepack enable
   pnpm install --frozen-lockfile
   ```

3. Start Convex and follow its prompts to create/select **your development deployment**:

   ```sh
   pnpm dev:backend
   ```

   Leave this terminal running so Convex generates types and synchronizes backend changes.

4. Convex creates `.env.local`. Add any missing variables from [.env.example](.env.example), keeping the deployment values generated by Convex:

   ```dotenv
   CONVEX_DEPLOYMENT=dev:your-deployment
   NEXT_PUBLIC_CONVEX_URL=https://your-deployment.convex.cloud
   NEXT_PUBLIC_CONVEX_SITE_URL=https://your-deployment.convex.site
   NEXT_PUBLIC_SITE_URL=http://localhost:3000
   NEXT_PUBLIC_TELEGRAM_AUTH_READY=false
   ```

5. In a second terminal, run `pnpm dev` and open [http://localhost:3000](http://localhost:3000).

Guest drafts are stored in the browser. You can build teams, change rulesets, browse references, switch languages, and print without Telegram. Signing in, cloud saves, and public sharing require the optional setup below.

## Optional Telegram sign-in

Use your own development bot and Telegram OIDC application. Never reuse the project's production bot, credentials, or webhook for a fork.

Configure these through the **Convex development dashboard**, never in a committed file or a `NEXT_PUBLIC_*` variable:

| Variable                 | Purpose                                       |
| ------------------------ | --------------------------------------------- |
| `TELEGRAM_BOT_USERNAME`  | Your bot's username, without `@`              |
| `TELEGRAM_BOT_TOKEN`     | Bot token from BotFather                      |
| `TELEGRAM_CLIENT_ID`     | Your Telegram OIDC client ID                  |
| `TELEGRAM_CLIENT_SECRET` | Your Telegram OIDC client secret              |
| `SITE_URL`               | `http://localhost:3000` for local development |
| `JWT_PRIVATE_KEY`        | Convex Auth RSA signing key                   |
| `JWKS`                   | Matching public JSON Web Key Set              |

Follow the [Convex Auth manual setup guide](https://labs.convex.dev/auth/setup/manual) to generate the signing key and JWKS. The backend and provider are already implemented; additional scaffolding is unnecessary.

Register `https://your-deployment.convex.site/api/auth/callback/telegram` as the exact development callback in BotFather. Leave `CUSTOM_AUTH_SITE_URL` unset in development so Convex Auth uses that callback. The browser returns to the origin in `SITE_URL` after sign-in. For production, see the [README](README.md#deployment).

Set `NEXT_PUBLIC_TELEGRAM_AUTH_READY=true` in `.env.local` once configured, then restart the frontend. Sign in and confirm guest drafts upload to your own account library.

The optional bot webhook is separate from sign-in: set `TELEGRAM_WEBHOOK_SECRET` in Convex and register your own bot's webhook at `https://your-deployment.convex.site/telegram-webhook` with that secret if you need private `/start` replies. Do not point a shared production bot at a development deployment.

## Working in the codebase

- Frontend code belongs in `src/`; backend code belongs in `convex/`.
- Read [AGENTS.md](AGENTS.md), and read [Convex's generated guidelines](convex/_generated/ai/guidelines.md) before editing backend code. For Next.js changes, consult `node_modules/next/dist/docs/`.
- Keep factual rules and catalogs in `src/domain/`. Read [rules provenance](docs/rules-sources.md) first, update explicit ruleset revisions when facts change, and compute costs through the shared validator. Development data has no backward-compatibility commitment.
- English is the source language. Keep both dictionaries in `src/i18n/` complete and use `gt-next` for interface copy. Proper player and skill names may remain English.
- Compose or wrap installed components in `src/components/ui/` and `src/components/magic-ui/`; do not patch vendor files directly.
- Preserve authenticated ownership checks and account isolation. Public team links must never expose owner IDs, Telegram IDs, or auth records.
- League and tournament management implementation is separate future work; avoid speculative scaffolding in unrelated changes.
- Keep secrets, `.env*` files (except `.env.example`), research downloads, and signing keys out of Git and issue/PR attachments.

## Checks and pull requests

Format your changed files and run:

```sh
pnpm format:check
pnpm check
pnpm test
pnpm build
```

`pnpm format` formats application code and documentation while respecting vendor/generated exclusions. Add meaningful tests for changes to rules, persistence, authentication, or recovery. For UI changes, exercise the affected flow locally and check narrow screens. For broader changes, check team creation, ruleset switching, draft restoration, English/Ukrainian switching, and owner/public UUID views.

Explain what changed, why, and which checks you ran in your pull request. Screenshots help with interface changes; reproducible steps and a source link help with rule corrections. Do not deploy to the maintainer's production backend. The maintainer bumps `package.json` before release to `main`.
